# Design Match: Interior Design Platform (CSIT314 Group Project)

Design Match (shown as **RenovationLink** in the UI) connects renovation customers with
interior designers. React provides customer and designer pages; Flask provides the API,
server-rendered administration pages, and SQLite storage. The budget chatbot searches the
same database and uses Groq to interpret requests and explain recommendations.

**Demo:** https://idp-design-match.onrender.com

The hosted demo resets its database when its container starts. Do not use it to store data
that needs to survive a restart. A successful deployment does not by itself verify Groq access.

| Area | Current implementation |
| --- | --- |
| Customer journey | Real login, project/designer browsing, details, saved projects and budget chat |
| Designer journey | Real company profile, portfolio management, photos, publishing and dashboard |
| Administration | Existing Flask/Jinja pages; React redirects admin and manager accounts there |
| Chat context | Budget, room, style and exclusions carry across messages; Show more, Cheaper, comparison and Start over |
| Data | Generated sample records stored in SQLite; the old React mock data and mock-only screens were removed |
| Validation | 563 Python tests collected; 63 frontend tests; merged main CI passed on 12 November 2026 |
| Coursework | Original user-story mappings and 12 detailed use-case diagrams are retained below; they are not a claim that every workflow has a React screen |

## 2. Run it

Requirements: **Python 3.12**, **Node.js 22** and npm. Run commands from the repository root.
The commands below use Windows PowerShell.

### Configure local development

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env       # first setup only; keep an existing .env
```

Edit `.env` locally. Set `LLM_API_KEY` to your Groq key and `SECRET_KEY` to a random secret.
Set `DB_PATH=platform.db`: the supplied example says `chatbot.db`, while the generator defaults
to `platform.db`. Using different files makes the app appear to have no generated users/projects.
Never commit `.env` or paste its secret values into logs, screenshots or PRs.

| Variable | Local/demo value or purpose |
| --- | --- |
| `LLM_API_KEY` | Full Groq key, entered as the value; the variable name must be exactly `LLM_API_KEY` |
| `LLM_BASE_URL` | `https://api.groq.com/openai/v1` |
| `LLM_MODEL` | `openai/gpt-oss-120b` |
| `LLM_FALLBACK_MODEL` | `openai/gpt-oss-20b` |
| `SECRET_KEY` | Nonempty random Flask session secret; generated by the Render Blueprint |
| `DB_PATH` | `platform.db` locally; `/app/platform.db` is the Docker default |
| `UPLOAD_DIR` | Optional; defaults to the app's `uploads` directory |
| `FRONTEND_DIST` | Leave unset for Vite development; use `frontend/dist` to serve a local production build |
| `LLM_TIMEOUT`, `LLM_TIME_BUDGET` | Optional seconds: default 10 per HTTP attempt and 20 per LLM step including retries |

`python app.py` loads `.env`; existing process environment variables take precedence. The data
generator and Gunicorn do not load that file themselves. Render must supply variables through
its service Environment settings. The Docker image excludes `.env`.

### Start Flask (terminal 1)

```powershell
$env:DB_PATH = "platform.db"
.\.venv\Scripts\python.exe scripts/generate_data.py --size 20
.\.venv\Scripts\python.exe app.py
```

**The generator deletes the database before reseeding it.** Run it for initial setup or an
intentional demo reset, not on every local code edit. Flask listens on http://127.0.0.1:5000.

### Start React (terminal 2)

```powershell
cd frontend
npm ci
npm run dev
```

Open http://localhost:5173. Vite proxies `/api`, `/uploads`, `/admin`, `/platform`, `/analytics`
and `/logout` to Flask. Both terminals must remain running. An anonymous `/api/auth/me` response
of 401 is expected before login; it does not mean the backend is down.

On macOS/Linux, use `.venv/bin/python` and `export DB_PATH=platform.db` for the Flask commands.

### Serve the built frontend locally

Stop Vite if it is no longer needed. Build React, then start Flask with its build directory:

```powershell
cd frontend
npm run build
cd ..
$env:FRONTEND_DIST = "frontend/dist"
.\.venv\Scripts\python.exe app.py
```

Open http://127.0.0.1:5000. The Dockerfile uses Gunicorn in production; this local command uses
Flask's development server. Remove `FRONTEND_DIST` from the terminal environment when returning
to the two-server development workflow.

## 3. How b-c-e maps to the code

A request always flows one way: **user → Boundary → Control → Entity → database**.

| Layer | Folder | Rule |
| --- | --- | --- |
| Boundary | `boundary/` + `templates/` | Flask routes and HTML pages. Accepts HTTP input, invokes controllers, and returns JSON or HTML. |
| Control | `control/` | Validates input and applies the acceptance criteria. Talks only to entities. |
| Entity | `entity/` | Data classes that load and save themselves. The only layer that touches SQLite (`db.py`) or uploaded files (`storage.py`). |

Controllers raise `ValueError` with a message the page can show (bad input) or `LookupError`
(not found, or someone else's data). Boundaries turn these into a red message or a 404.

Shared helpers inside the control layer: `validation.py` (email, numbers, dates, images),
`ownership.py` (a designer may only change their own projects) and `generate_report_controller.py`
(the parent class of the three report controllers).

```
design-match/
├── app.py                    # creates the Flask app and registers every boundary
├── boundary/                 # 8 route modules (pages)
│   ├── auth_boundary.py      #   LoginPage, RegisterPage, Log out
│   ├── account_boundary.py   #   User Admin: accounts and profiles
│   ├── company_boundary.py   #   Designer company info + public company page
│   ├── idp_boundary.py       #   Browse/search/filter, IDP detail, Create IDP
│   ├── portfolio_boundary.py #   Designer's own projects: edit, publish, status, photos, delete
│   ├── favourite_boundary.py #   Save / remove, My favourites
│   ├── analytics_boundary.py #   Designer interest tracking
│   └── platform_boundary.py  #   Categories, reports, dashboard
├── control/                  # application use cases, validation, ranking and ownership checks
├── entity/                   # UserAccount, UserProfile, Company, TeamMember, Category, IDP,
│                             # IDPPhoto, Favourite, ViewEvent, Notification, Report
├── templates/                # Bootstrap pages, one folder per actor
├── tests/                    # pytest unit tests
├── scripts/generate_data.py  # test data generator
├── frontend/                 # React app (boundary layer for visitors, customers, designers)
└── .github/workflows/ci.yml  # CI/CD pipeline
```

## 3a. React and Flask: one app, one database

React is a second **boundary**: its HTTP requests reach controllers through the JSON API in
`boundary/*.py`. Business records come from Flask/SQLite. React still holds transient UI state,
and the chat stores messages/preferences in browser-tab `sessionStorage` across reloads.
The former `mockData.js` and mock request service were removed. Test doubles remain in tests.
Mock-only payments, consultations, packages, enquiries and reviews are no longer exposed as
working React features; their removal does not implement equivalent backend workflows.

| Who | Uses | Why |
| --- | --- | --- |
| Visitor, Customer | React | Browse/search/filter projects, project details, designers, company pages, favourites, chatbot |
| Interior Designer | React | Dashboard, My projects (create, edit, tags, photos, publish, current/past, delete), company profile. The deeper reports (rank, trends, compare, CSV) open the Flask `/analytics` pages. |
| User Admin, Platform Management | Flask pages | They log in through React and are handed to `/admin/accounts` or `/platform/` with the same session cookie (no second login). Flask's Log out returns to the React login. |

React pages have real addresses, so refresh, Back and shared links work. They use `#/…` so they can
never clash with Flask's own paths: `#/projects`, `#/projects/12`, `#/designers`, `#/designers/3`,
`#/favourites`, `#/designer`, `#/designer/projects`, `#/designer/projects/new`,
`#/designer/projects/12`, `#/designer/company`.

Most JSON endpoints return a `data` envelope or a structured `error`. Chat responses and
chat diagnostics use their own top-level fields, such as `reply`, `source` and `configured`:

Draw each diagram with exactly these class and method names, and the design will match the code.
Every use case has the precondition "user is logged in with the right role" (no «include» Log in).

| US-54 Create IDP | `CreateIDPPage → CreateIDPController.create_idp(designer_id, title, ...)` | `→ Category.find_by_name` (check), `→ IDP.create(...)` |

Example in full, US-54:

```
Designer -> CreateIDPPage : submit form
CreateIDPPage -> CreateIDPController : create_idp(designer_id, title, description, category, budget, ...)
CreateIDPController -> CreateIDPController : validate input (required fields, budget > 0, tags <= 5)
CreateIDPController -> Category : find_by_name(category)
Category --> CreateIDPController : active category
CreateIDPController -> IDP : create(...)
IDP --> CreateIDPController : new IDP
CreateIDPController --> CreateIDPPage : new IDP
CreateIDPPage --> Designer : show the project page
```

## 6. Data model (SQLite)

| Table | Main columns | Notes |
| --- | --- | --- |
| user_profile | name, description, status | The 4 built-in roles are created automatically |

| team_member | company_id, name, position | |
| category | name, description, status, created_at | 5 defaults created automatically |
| idp | designer_id, title, description, category, budget, style_tags, property_type, location, completion_date, status (Current/Past), published (draft = 0), views, created_at | |
| idp_photo | idp_id, filename, is_cover | Files stored in `uploads/` |
| favourite | customer_id, idp_id, saved_at | A save = one shortlist |

| notification | designer_id, idp_id, message, is_read | View and shortlist milestones |

Deleting a project also deletes its photos, favourites and view history (`ON DELETE CASCADE`).

## 7. Test-driven development

Run backend checks from the repo root, then frontend checks from `frontend`:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pytest --cov=control --cov=entity --cov=boundary
cd frontend
npm test
npm run build
```

If Windows temporary-directory permissions prevent pytest setup, use a new writable directory:
`python -m pytest -q --basetemp=.pytest-local-tmp`. Pytest may clear this directory; do not point
it at a folder containing work you want to keep.

The current checkout collects **563 Python tests** and has **63 frontend tests**. Gateway tests
use a fake HTTP transport; passing them does not prove that a deployed key can call Groq.
On 12 November 2026, local authenticated Groq checks and a two-message conversation succeeded
with `source: "llm"`, three results, and Modern/Kitchen context retained as the budget changed
from 10,000 to 8,000. Repeat the deployed checks after changing Render configuration.

- Each acceptance criterion is one test. The 12 detailed use cases each have their own test file
  (`tests/test_<controller>.py`); the other stories are grouped by feature (`test_accounts_and_profiles.py`,
  `test_company.py`, `test_portfolio.py`, `test_customer.py`, `test_interest_tracking.py`, `test_platform.py`).
- `test_boundary.py` drives the real pages as each of the four roles. `test_generate_data.py` checks the generator.
- Every test gets a fresh, empty database and upload folder (`tests/conftest.py`).

For the report: for at least one story per member, commit the failing test first (red), then the code (green),
and screenshot both runs. The commit history is the TDD evidence.

## 8. CI/CD

`.github/workflows/ci.yml` runs on pull requests and pushes to `main`:

1. installs the requirements,
2. runs all tests with a coverage report,
3. runs `generate_data.py --size 20` to prove the demo data still builds,
4. installs the locked frontend dependencies, runs frontend tests, and builds React,
5. on `main` only, after both jobs pass, calls the Render deploy hook if `RENDER_DEPLOY_HOOK` is configured.

### Deploy the resettable demo

1. Merge the deployment changes into `main` after CI passes.
2. In the [Render dashboard](https://dashboard.render.com), choose **New → Blueprint**,
   authorize GitHub access, and select `Shariff98/CSIT314-IDP` with branch `main`.
3. Use the repository's `render.yaml`. It defines a Docker web service and generates `SECRET_KEY`.
4. When prompted for `LLM_API_KEY`, enter your key from the [Groq console](https://console.groq.com/keys)
   directly in Render. Do not commit the key to GitHub.
5. Apply the Blueprint and inspect the first build and startup logs, then open the service URL.

The Dockerfile builds React with Node 22, installs the Python dependencies, and serves the
built frontend and Flask API from the same address using Gunicorn. `FRONTEND_DIST` points
to the built frontend; no separate frontend host or manual build/start command is needed.

**This is a resettable demo.** Every container start runs `generate_data.py --size 20`,
which deletes and recreates the database. User changes do not survive that reset, and
uploaded files have no persistent disk. The demo uses 20 designers and 20 customers,
including `customer0@example.com`, with password `password123`.

To trigger deployments from GitHub CI, optionally save Render's Deploy Hook URL as the
repository Actions secret `RENDER_DEPLOY_HOOK`. The workflow skips the hook when it is absent.
If using this hook as the only deployment trigger, disable Render's separate automatic
deployments to avoid duplicate deployments.

## 9. Test data

`scripts/generate_data.py` inserts synthetic sample records into the real SQLite database.
These are the records used by the project API, designer directory and chatbot—not a second
frontend dataset. Images are generated placeholder PNGs, not real renovation photography.

| Data | Render / `--size 20` | Default local generation (`--size 100`) |
| --- | --- | --- |
| Accounts | 42: admin, manager, 20 designers, 20 customers | 202: admin, manager, 100 designers, 100 customers |
| Companies | 20 | 100 |
| Projects and generated cover photos | 60, including drafts | 300, including drafts |
| Categories | 20 | 20 |
| Profiles | 5 | 5 |
| Team members, views, favourites, notifications | Generated from the smaller sample | Generated from the larger sample |

The generator uses random seed 314, but timestamps are relative to the generation date.
Some accounts are suspended and some projects are drafts to exercise access rules. The
public APIs and chatbot do not show unpublished projects. Uploaded photos use `uploads/`.
Neither `.db` files nor uploads belong in Git; Render recreates this disposable data at startup.

### Troubleshooting

| Symptom | Check / action |
| --- | --- |
| Local page cannot reach its API | Keep Flask on port 5000 and Vite on 5173 running; check the Vite proxy |
| Login fails or projects are empty | Confirm app and generator use the same `DB_PATH`; use a generated active account |
| Chat answers without the AI service | Inspect `/api/chat/status`; configured=false means no usable key was loaded |
| HTTP 401 from Groq | Check the key value, validity and expiry in the environment of the running service |
| HTTP 404 model_not_found | Remove retired model overrides; check model availability/access in Groq |
| HTTP 429 or timeouts | Inspect provider limits/connectivity and runtime logs; retries are bounded |
| Old error still visible after fixing settings | Send a new message or select Start over; old chat messages persist in the browser tab |
| Render builds successfully but chat falls back | `/login` only checks web-service health; use `/api/chat/status?check=1` to test Groq |
| Data disappears after a Render restart | Expected: startup reseeds the demo database |

The connection check makes a small real provider request and counts against the chat rate limit.
Logs/status expose sanitized failure categories, not API keys or provider error bodies.

## 10. Ethics and security built into the code

- Passwords are stored only as salted hashes (Werkzeug `generate_password_hash`).
- Suspending an account or a profile blocks login but keeps the data (no silent deletion).
- Designers can only see and change their own drafts, projects, photos and statistics (`control/ownership.py`).
  Someone else's project returns "not found", so drafts can't be discovered.
- Customers' favourites are private; designers see only counts, never who saved a project.
- View counts ignore the owner and repeat views in one session, so statistics aren't inflated (US-37).
- Uploads are limited to image types and 5 MB, and stored under random file names.

Known limits, worth a line in the report: forms have no CSRF tokens (add Flask-WTF before real use),
and custom user profiles (US-51) can be created and assigned but don't unlock extra pages; only the
four built-in roles have pages.
